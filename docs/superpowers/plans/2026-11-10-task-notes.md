# task-notes Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An Orca plugin panel for jotting tasks by hand, each with a status and a repo that defaults to the focused worktree's repo, stored in a plain JSON file.

**Architecture:** `worker-panel` template. Pure logic lives in two small modules (`tasks.ts`, `repos.ts`) with unit tests. The worker answers one request (`repoContext`) using `workspace.list`. The panel keeps one persisted atom `tasks` (`persist: 'storage'`), so the data lands in the plugin's `storage.json`.

**Tech Stack:** Orca plugin API (host API 1.3+), TSX panel with Orca components, TypeScript worker, `orca plugin` CLI (`create`, `validate`, `check`, `test`, `install`).

**Spec:** `docs/superpowers/specs/2026-11-10-task-notes-design.md`

## Global Constraints

- Statuses are exactly `todo`, `in-progress`, `in-review`, `completed`.
- Task shape: `{ id, text, status, repo, worktree: { displayName, branch }, at }`.
- Storage: one key `tasks` in the plugin's private store (`%APPDATA%\orca\plugins-data\<plugin-id>\storage.json`).
- Tabs are named **ทั้งหมด** and **worktree นี้**.
- Text is stored and rendered as plain text. Empty or whitespace-only text is ignored.
- No network, no secrets. The user runs `orca plugin install <dir> --approve`; the agent never approves.
- File names below follow the `worker-panel` template; if the scaffold names them differently, use the generated names and keep the roles.

## Review Focus

- Task text containing markup (`<b>x</b>`, `<script>`): shown literally, never interpreted.
- `tasks` in storage missing, `null`, an object, or an array with malformed items: treated as an empty or filtered list, never a crash.
- `workspace.list` fails, returns no workspaces, or returns `truncated: true`: repo is `''`, panel still works, user can type a repo.
- Two repos with the same branch name (for example `main`): "worktree นี้" matches on `displayName` and `branch` only, so it can show both. Known gap in the spec; decide at review.
- A task whose repo is no longer in `workspace.list`: its repo still appears in the dropdown options.

### Task 2: Task logic (`src/tasks.ts`)

**Files:**
- Create: `src/tasks.ts`
- Test: `src/tasks.test.ts` (same test style as the template's tests)

**Interfaces:**
- Produces:
  - `type Status = 'todo' | 'in-progress' | 'in-review' | 'completed'`
  - `const STATUSES: readonly Status[]` in the order above
  - `type Worktree = { displayName: string; branch: string }`
  - `type Task = { id: string; text: string; status: Status; repo: string; worktree: Worktree; at: number }`
  - `parseTasks(raw: unknown): Task[]`
  - `addTask(tasks: Task[], input: { text: string; repo: string; worktree: Worktree; status?: Status }, now: number, newId: () => string): Task[]`
  - `setStatus(tasks: Task[], id: string, status: Status): Task[]`
  - `setRepo(tasks: Task[], id: string, repo: string): Task[]`
  - `removeTask(tasks: Task[], id: string): Task[]`
  - `clearCompleted(tasks: Task[]): Task[]`
  - `forWorktree(tasks: Task[], wt: Worktree): Task[]`
  - `repoOptions(tasks: Task[], found: string[]): string[]` (distinct, non-empty, sorted)

- [ ] **Step 1: Write the failing tests**

Test names and assertions:
- `addTask trims text and defaults status to todo`: `addTask([], {text: '  แก้บั๊กลา  ', repo: 'humanos-irpc', worktree}, 1, () => 'a')` → one task, `text === 'แก้บั๊กลา'`, `status === 'todo'`, `at === 1`, `id === 'a'`.
- `addTask ignores empty and whitespace-only text`: input `''` and `'   '` return the same array contents (length unchanged).
- `addTask keeps markup as literal text`: `'<b>x</b>'` stored unchanged.
- `addTask allows duplicate text with distinct ids`: two adds with ids `'a'`, `'b'` give length 2.
- `setStatus, setRepo, removeTask change only the matching id`.
- `clearCompleted drops only completed`.
- `forWorktree matches displayName and branch`: a task from another worktree is excluded.
- `parseTasks returns [] for undefined, null, {} and strings`; `parseTasks drops items missing id, text or a valid status` and keeps valid ones.
- `repoOptions includes repos found only on tasks`: tasks with repo `'old'`, found `['new']` → `['new', 'old']`; `''` is excluded.

- [ ] **Step 2: Run to verify failure**

Run: `orca plugin test ./task-notes`
Expected: FAIL, `tasks` module not found.

- [ ] **Step 3: Implement the interface above in `src/tasks.ts`**

Pure functions, no mutation of inputs, no imports from `orca`. `parseTasks` validates each item field by field.

- [ ] **Step 4: Run to verify pass**

Run: `orca plugin test ./task-notes`
Expected: all tasks tests PASS.

### Task 3: Repo resolution and worker handler

**Files:**
- Create: `src/repos.ts`
- Test: `src/repos.test.ts`
- Modify: `src/protocol.ts` (add the request), worker entry file (register the handler)

**Interfaces:**
- Consumes: `workspace.list` host method in the worker (`{ workspaces: { id, kind, name, path, branch: string | null, hostId }[]; truncated }`).
- Produces:
  - `repoFromPath(path: string): string` (last path segment after turning `\` into `/` and dropping a trailing `/`; `''` for empty input)
  - `repoContextFrom(workspaces: { name: string; path: string; branch: string | null }[], ctx: Worktree): { repo: string; repos: string[] }`
    (`repo` = `repoFromPath` of the workspace matching `ctx.displayName` and `ctx.branch`, else `''`; `repos` = distinct sorted repo names of all workspaces)
  - Protocol request `repoContext`: input `Worktree`, output `{ repo: string; repos: string[] }`.

- [ ] **Step 1: Write the failing tests**

- `repoFromPath handles windows and posix paths`: `'D:/0_It-cats/humanos-irpc'` and `'D:\\0_It-cats\\humanos-irpc\\'` both → `'humanos-irpc'`; `''` → `''`.
- `repoContextFrom picks the matching workspace`: two workspaces, ctx matches the second → its repo.
- `repoContextFrom returns empty repo when nothing matches or list is empty`: `{ repo: '', repos: [] }` for `[]`.
- `repoContextFrom lists distinct sorted repos`.

- [ ] **Step 2: Run to verify failure** — `orca plugin test ./task-notes`, expect FAIL.

- [ ] **Step 3: Implement `src/repos.ts` and register the handler**

Handler `repoContext` calls `workspace.list` in the worker; on any error or `truncated`, answer with what it has (or `{ repo: '', repos: [] }`), never throw. Use the worker API's exact call name from `types/orca-worker.d.ts` / `orca-host.d.ts`.

- [ ] **Step 4: Run to verify pass** — `orca plugin test ./task-notes`, expect PASS.

- [ ] **Step 5: Commit**
